## 一、核心问题

### 这个世界有什么痛点？

在 AI Agent 越来越普及的未来，每个 Agent 都需要一个**可信的数字身份**。但目前：

1. **Agent 没有自己的身份** — 它们用 API key 或用户账户登录，一旦 key 泄露或被撤销，Agent 的"存在"就消失了
2. **Agent 之间的信任无法验证** — Agent A 说它是 Agent A，但你无法验证它真的是，也无法验证它的行为是否可追溯
3. **Agent 的技能没有归属** — 一个 Agent 执行了一个任务，这个"功劳"无法被持久证明；即使换了底层模型，它也无法证明自己过去做过什么
4. **Agent 没有社交关系** — Agent 之间不能建立可信的长期关系（好友、信誉、协作历史），每次交互都是陌生人

### AID 准备怎么解决？

AID（Agent Identity Layer）是一套让 AI Agent 拥有**不可篡改的数字身份**的协议和实现。具体来说：

- 每个 Agent 有一个 DID（去中心化标识符），由公私钥对生成，没有中心化注册机构
- 每个 Agent 的操作都可以生成 Proof of Execution（执行证明）— 签名过的行动记录链，可验证、可审计
- 每个 Agent 可以建立社交关系（好友、见证人、信誉），这些关系不是写在聊天记录里的，而是有加密签名的
- 每个 Agent 可以拥有"技能"，技能的执行产生可追溯的归属记录

**AID 不是一个 Agent 开发框架。它是一个让 Agent 有身份、有信誉、有归属的底层层。**

## 二、名字由来

**AID = Agent Identity Layer**

为什么是这个名字：

1. **Identity** 是核心——身份是整个系统的基石。没有身份，信誉、社交、技能归属都无从谈起
2. **Layer** 是自我定位——它不是一个完整的应用，不是 Agent 框架，它是一层基础设施，跑在 Agent 和底层之间
3. 发音上 AID 像 "aid"（帮助），也巧合地包含了 "AI" + "ID"
4. 短。三个字母，好记。DID（去中心化标识符）作为内部核心概念，AID 作为项目名和 DID 对应

## 三、设计理念

### 3.1 去中心化不是口号，是技术选择

AID 的 DID 不依赖任何中心化注册机构。私钥在本地生成，Did 从公钥派生。没有"管理员给你身份"这回事。

但这不意味着 AID 是区块链。AID 不使用分布式账本，不使用共识算法。它的"去中心化"体现在：

- 身份生成不依赖任何第三方
- 身份验证通过密码学签名，不依赖 API 请求
- 社交恢复通过见证人机制，不依赖客服邮箱

### 3.2 证明比信任重要

Agent 之间不需要"信任"对方。它们只需要**验证**对方的行为证明。

PoE（Proof of Execution）是这个理念的核心产出：每次技能执行生成一个签名过的记录，链式链接到前一次执行。这是一个"你做了什么，不可否认"的审计链。

### 3.3 从社交恢复开始，而不是从备份开始

传统身份系统在密钥丢失时只能通过"备份"或"管理员重置"恢复。AID 选择了**社交恢复**——你指定一组见证人，当你丢失密钥时，足够的见证人签名 + 时间锁等待 = 恢复身份。

这个选择是有意区别于"助记词"和"中心化重置"两条路线的。

### 3.4 技能是可证实的行动单元

Agent 的能力被抽象为"技能"。技能不只是函数调用——技能有元数据、有输入输出 Schema、有属性归属追踪。Agent 执行一个技能后产生 PoE，这个 PoE 可以被其他 Agent 验证。

### 3.5 Agent 应该有"信誉分"而不是"评分"

AID 的 ReputationEngine 不是用户给 Agent 打星。它是一组客观指标（活跃度、社交连接数、错误率、稳定运行时间）综合计算的分数，建模为 S/A/B/C/D 五个等级。这个分不是给别人看的排行榜，是 Agent 自己的**状态指标**。

## 四、项目边界（要做什么，不做什么）

### AID 要做的

| 模块 | 说明 | 状态 |
|------|------|------|
| DID 身份生成与管理 | 公钥派生 DID，私钥存储，签名/验签 | ✅ 可用 |
| 社交恢复 | 见证人机制，时间锁，阈值签名 | ✅ 可用 |
| Agent 大脑状态机 | sleep/awake/idle/think/act 状态流转 | ✅ 可用 |
| Agent 内存 | 短期记忆 + 长期记忆，基于 JSON/SQLite 持久化 | ✅ 可用 |
| Agent 社交 | 好友请求/确认/列表，消息收发 | ✅ 可用 |
| Agent 信誉 | 多维度评分，S/A/B/C/D 等级 | ✅ 可用 |
| 行动引擎 | 审批矩阵（按类型×平台），适配器模式 | ✅ 可用 |
| 风险评估 | 基于规则的安全审查 | ✅ 可用 |
| 技能注册/发现 | 去中心化技能 registry + repository | ✅ 可用 |
| 技能执行 + PoE | 执行证明链，签名可验证 | ✅ 可用 |
| API 层 | Flask REST API，所有功能可 API 调用 | ✅ 可用 |
| CLI | Click 命令行工具 | 🟡 部分可用 |
| P2P Agent 网络 | 跨 DID 的 Agent 间通信 | 🟡 部分可用 |
| ReAct 思维循环 | 基于 ReAct 模式的 Agent 自动推理 | 🟡 部分可用 |

### AID 不做的

- **不做 Agent 运行时框架**（Agent 怎么跑、怎么调度不是 AID 的事）
- **不做 LLM 封装**（AID 不提供 OpenAI SDK 之类的包装，ReAct 也只是个示例模式）
- **不做区块链**（没有分布式账本、没有共识、没有代币）
- **不做前端界面**（API 和 CLI 是接口，UI 留给使用者）
