1. 核心概念与名词解释

Alpha-ID (数字灵魂 / Ghost Layer)

定义： 坐在所有 AI 工具之上的统一身份层，提供跨平台的身份、记忆和操作能力。

核心理念： "你不是一个人在数字世界里流浪。Alpha-ID 是你的数字灵魂——带着你的身份、用着你的大脑、长着你的手脚。未来你一个意念，它就到。"

关键特征： 统一身份、孪生大脑、眼睛和手脚、社交生态、自主学习

DID (去中心化身份标识符 - Decentralized Identifier)

定义： W3C 标准的去中心化身份标识符，在 Alpha-ID 中格式为 did:aid:xxx。

实现： 使用 Ed25519 算法生成密钥对，私钥存储在本地 ~/.alpha-id/keys/ 目录。

用户感知： 用户不直接接触 DID 技术术语，只感知"它认识我"的体验。

TwinBrain (孪生大脑)

定义： Alpha-ID 的核心引擎，包含三层记忆架构和 ReAct Agent 引擎。

三层记忆：

  • 工作记忆： 当前会话 + 最近 20 条上下文
  • 情景记忆： 今天做了什么、跟谁聊过、学到了什么
  • 语义记忆： 偏好、习惯、知识图谱（个性化核心）

Computer Use (计算机使用能力)

定义： Alpha-ID 替用户操作计算机的能力，通过三层闭环实现。

三层架构：

  • Plan 层： 意图分解为 N 步执行计划（待建）
  • Skill 层： 具体工具如截图、OCR、窗口控制（已实现）
  • Safety 层： 敏感操作暂停、异常回滚、录屏审计（待建）

MCP (Model Context Protocol)

定义： Anthropic 开发的协议，用于 AI 工具与外部服务通信。

在 Alpha-ID 中的作用： 作为身份注入的通道，让 Claude Desktop 等支持 MCP 的工具认识用户。

现状： MCP Server 已实现但 P0 阶段暂不启用。

A2A (Agent-to-Agent)

定义： Agent 间通信协议，用于社交生态建设。

在 Alpha-ID 中的作用： 实现 Agent 间的 DID 互认、技能交换、信誉共享。

现状： 推迟到 P1-2 阶段实现。

Profile (人格画像)

定义： 从用户数字痕迹中提取的完整人格描述。

包含字段： 总结、风格、活跃时段、关注话题、技术偏好等。

数据源： ChatGPT 导出、Claude 导出、浏览器历史、GitHub 活动等。

5. 开发流程与规范

代码规范

  • 引号： 双引号
  • 缩进： 4 空格
  • 行长： ≤ 120
  • 格式化： 遵循 ruff.toml 规则
  • Python 版本： 3.12+
  • 类型注解： 完整类型注解，pyright basic

测试策略

  • 测试框架： pytest
  • 覆盖率目标： ≥68%
  • 测试类型： 单元测试 + 端到端用户故事测试
  • 现有测试： 855+ 测试（852 passed, 3 skipped）

禁止事项

  • ❌ 禁止引入 LangChain 作为依赖
  • ❌ 禁止修改已有测试文件（除非只改预期值）
  • ❌ 禁止发 git commit / 建分支
  • ❌ 禁止加版权头
  • ❌ 禁止改与当前任务无关的代码
  • ❌ 每次改动前必须读 PLAN.md 确认当前阶段

核心原则

  1. Don't touch stable code — 803+ passing tests stays untouched. Add new files, don't modify stable logic.
  2. Only build what would break if missing — Don't build "might be useful later". 砍掉的不够，接着砍。
  3. Graceful degradation — Works without API key, without GPU, without internet.
  4. User feels effects, not technology — Users never say "DID" or "Ed25519". They say "it knows me".
  5. Single-developer efficiency — 700 行闭环比 1500 行半成品强一万倍。

6. 六框架方法论

框架 核心理念 自检问题 交付检查
宇宙星链 点→线→面→球→球变新点→复刻。多维发散，不是线性扩散。 我是不是只在一个维度看问题？向四周扩散了没有？ 这次交付是独立的点，还是能自动生长出下一节点？
第一性原理 压缩到本质后重新组装，不是只分析没重建。 压缩到本质后我重新组装了吗？还是只分析了没重建？ 我交付的是表层描述，还是压缩到本质后的重建方案？
反向推翻 主动寻找反例，排除最可能的死因。 如果我的判断是错的，最可能的死因是什么？排除了吗？ 交付的内容如果被用户推翻，最大漏洞可能是什么？我事先补了吗？
递归降维 复杂问题降一层先验证小结论。 当前问题太复杂的话，降一层能不能先验证一个小结论？ 有没有在太高维度讨论，而降维到可执行的具体环节？
反脆弱 设计有益的失败路径，越用越强。 这次犯错能让我下次更强吗？机制记下来了没有？ 交付的方案如果遇到失败，有容错路径吗？
节律控制 控制扩散/收敛节奏，适时输出可执行方案。 我是在一直扩散不收缩，还是已经准备好输出可执行方案了？ 这次交付是新方向的扩散，还是已有方向的收敛执行？节奏对吗？

六框架联动流程

宇宙星链（告诉我"生态坐标"）
      ↓
第一性原理（告诉我"本质是什么"）
      ↓
反向推翻（告诉我"为什么不会死"）
      ↓
递归降维（告诉我"先从哪一层下手"）
      ↓
反脆弱设计（告诉我"怎么越用越强"）
      ↓
节律控制（告诉我"现在该扩散还是收缩"）
      ↓
通过 → 执行
不通过 → 回到宇宙星链重新定位

7. 并行工作线程分配

作为 AI 编码代理，我可以并行处理以下 4 条工作线程：

线程 1：P0 阶段完善与测试加固

  • 完成 ChatGPT 采集器的边缘情况处理
  • 增强用户故事端到端测试覆盖
  • 优化 Profile CLI 的用户体验
  • 修复已知的 minor bugs
  • 确保 7/15 PyPI v0.1.0 发布准备就绪

优先级： 🔴 最高（直接影响 P0 交付）

线程 2：P1 阶段功能预研与设计

  • 研究 Claude 数据导出格式，设计 Claude 采集器
  • 设计 3 问题向导交互流程
  • 规划 MCP 身份注入的技术方案
  • 设计 Web 画像仪表盘的 UI/UX
  • 评估 Codex 采集器的可行性

优先级： 🟡 中等（为 P1 阶段做准备）

线程 3：基础设施与开发体验优化

  • 完善 Docker Compose 配置
  • 优化 taskipy 开发命令
  • 改进文档和 README
  • 设置 CI/CD 自动化流程
  • 集成安全扫描工具（Bandit）

优先级： 🟢 较低（支撑性工作）

线程 4：Computer Use 能力扩展

  • 设计 Plan 层意图分解算法
  • 规划 Safety 层风险控制机制
  • 扩展 Screen Capture 和 OCR 功能
  • 研究 Browser Use 集成方案
  • 设计桌面精灵悬浮球增强功能

优先级： 🟡 中等（远期能力建设）

任务分配原则

  1. 按优先级顺序执行： 线程 1 > 线程 2 ≈ 线程 4 > 线程 3
  2. 避免冲突： 各线程工作在不同模块，减少代码冲突
  3. 增量交付： 每个线程产出可独立验证的小功能
  4. 六框架检验： 每个任务交付前过六框架自检
  5. 用户确认： 关键决策点需要用户确认后再继续
